# V5.1 自建轻量 IM — 技术方案（最终选型）

> **版本**: v1（2026-07-08）
> **决策**: 不用第三方 IM 服务商，**自建轻量群聊**，跑在现有技术栈上（NestJS + Postgres + Railway + R2 + APNs）。
> **依据**: ① 大陆用户对 api.starlensai.com 的连通性已被线上验证，自建 = 与现有 App 完全一致的连通性；② 家庭群 ≤10 人、低频、无陌生人社交，不需要完整 IM；③ 零认证、零月费、零厂商锁定，数据全在自己库里。
> **交互基准**: 尽可能与微信一致（详见 §7 对齐清单）。
> **配套**: V5.1_需求文档-家庭IM互动.md（产品需求不变）、V5.1_技术架构与开发任务.md（其中腾讯云 Chat 相关章节由本文取代）、V5.1_UI_Mockups.html。

## 1. 总体架构

```
┌─ iOS ──────────────────────────────┐        ┌─ Server (NestJS on Railway) ──────────┐
│ FamilyChatView（微信式群聊 UI）      │  WSS   │ chat-gateway（@nestjs/websockets/ws）  │
│ ChatSyncEngine                      │◄──────►│  ├ JWT 鉴权握手                        │
│  ├ 本地存储 SQLite（GRDB）           │        │  ├ 在线连接表（userId→conn）           │
│  ├ seq 增量同步 + 断线补拉           │  REST  │  └ 新消息实时下发                      │
│  ├ 发送队列（重试/去重）             │◄──────►│ chat 模块（REST）                      │
│  └ 已读游标上报                     │        │  ├ send / pull / recall / read        │
│ 录音 + SFSpeechRecognizer 转文字     │        │  ├ media 直传 R2（复用现有上传）        │
│ 图片/语音上传 R2（复用现有链路）      │        │  └ 频控 / 尺寸 / 权限校验              │
└────────────────────────────────────┘        │ family-event.service（卡片=特殊消息）   │
          ▲ APNs（离线推送，复用现有 PushService│ apns-push（离线成员推送，复用现有）      │
            与 V5.1 强提醒通道）                └────────────────────────────────────────┘
```

原则：**Postgres 是消息的唯一事实源；WebSocket 只是"加速器"** —— WS 挂了，轮询 + APNs 也能收到消息，聊天页永远可用（降级无感）。

## 2. 数据模型（Prisma 增量）

```prisma
model FamilyMessage {
  id          String    @id @default(cuid())
  groupId     String    @map("group_id")
  seq         BigInt                              // 组内单调递增，同步协议的核心
  senderId    String?   @map("sender_id")         // null = 系统/官方
  type        String                              // text/voice/image/bigEmoji/card/system
  content     String?   @db.Text                  // text 正文 / 语音转文字 / 系统提示语
  payload     Json?                               // 各类型扩展：card 全量、voice{url,duration}、image{url,w,h,thumb}
  eventId     String?   @map("event_id")          // type=card 时关联 family_events
  clientMsgId String?   @map("client_msg_id")     // 客户端 UUID，幂等去重
  status      String    @default("normal")        // normal / recalled
  version     Int       @default(1)               // 卡片更新（求助去重改卡）时 +1
  createdAt   DateTime  @default(now()) @map("created_at")

  @@unique([groupId, seq])
  @@unique([groupId, clientMsgId])                // 重发去重
  @@index([groupId, seq(sort: Desc)])
  @@map("family_messages")
}

model FamilyReadCursor {
  groupId     String   @map("group_id")
  userId      String   @map("user_id")
  lastReadSeq BigInt   @default(0) @map("last_read_seq")
  updatedAt   DateTime @updatedAt @map("updated_at")
  @@id([groupId, userId])
  @@map("family_read_cursors")
}

// family_group 增量：
// lastSeq BigInt @default(0)  — 发消息时事务内 +1（SELECT ... FOR UPDATE），彻底避免 seq 冲突
```

要点：
- **seq 是一切的锚**：未读数 = `group.lastSeq - myCursor.lastReadSeq`；已读名单 = `cursor.lastReadSeq >= msg.seq` 的成员；增量同步 = `WHERE seq > :afterSeq`。不需要逐条已读表、不需要逐条未读表。
- 卡片就是一条 `type=card` 的消息，`family_event` 表职责不变（统计事实源）；求助卡去重更新 = 改原消息 payload + version+1，WS 广播 `update` 事件。
- 撤回 = `status=recalled` 墓碑（内容置空），客户端渲染"XX 撤回了一条消息"。
- 消息永久保留（家庭消息量极小，一个活跃家庭一年 < 1 万条，存储可忽略）。

## 3. 同步协议（核心，微信同款思路：拉为主、推为辅）

### 3.1 发送（客户端 → 服务端）

```
1. 用户点发送 → 本地立刻落库（state=sending，clientMsgId=UUID）、立刻上屏
2. POST /api/chat/messages { groupId, clientMsgId, type, content, payload }
3. 服务端事务：group.lastSeq+1 → 写 family_messages → 返回 { seq, id, createdAt }
4. 客户端把本地消息标记 sent、记录 seq
5. 失败：自动重试 3 次（clientMsgId 幂等，不会重复入库）；仍失败 → 红色 ❗，点击重发（微信同款）
```

### 3.2 接收（三条通道，同一入口收敛）

| 通道 | 时机 | 动作 |
|---|---|---|
| WebSocket | App 前台且连接存活 | 服务端发 `{op:"new", groupId, seq}` 轻通知 → 客户端按 seq 增量拉取 |
| APNs | 离线/后台 | 推送带 groupId → 点开后按本地 lastSeq 增量拉取 |
| 主动拉取 | 进入聊天页 / 前台激活 / WS 重连成功 / 下拉 | `GET /api/chat/messages?groupId=&afterSeq=&limit=50` |

**关键设计：WS 只发"有新消息"的信号，不发消息体** —— 消息体永远走同一个增量拉取接口。好处：三条通道殊途同归，没有消息体两套投递路径的一致性问题；乱序、丢包、重连全部靠 seq 补齐，客户端逻辑只有一种："我有 lastSeq，找服务器要 afterSeq 之后的"。

### 3.3 历史回溯与多端

- 向上翻历史：`GET /messages?groupId=&beforeSeq=&limit=30`；
- 换机/新设备：本地库为空 → 先拉最近 50 条即可用，历史按需回溯（微信同款体验）；
- 多端同时在线：同一账号每端各自维护 lastSeq，天然一致。

### 3.4 已读

- 聊天页可见且滚到底 → `PUT /api/chat/read-cursor { groupId, seq }`（节流：2s 最多一次）；
- 服务端 WS 广播 `{op:"read", groupId, userId, seq}` → 他人界面"已读"状态实时变化；
- 卡片已读回执：family_event.readBy 由 read-cursor 变更事件驱动回写（seq 覆盖到卡片消息即算已读）。

### 3.5 WebSocket 细节

- `wss://api.starlensai.com/chat`，握手带 JWT；心跳 ping/pong 30s，2 次无响应断开重连（指数退避 1/2/4/8s 封顶）；
- Railway 单实例内存连接表即可（当前规模）；将来多实例 → Redis pub/sub 扇出（预留接口，不先做）；
- **降级**：WS 不可用时，聊天页前台以 5s 轮询增量接口兜底（用户无感），页面退出即停。

## 4. 推送（复用现有体系）

| 场景 | 通道 | 规则 |
|---|---|---|
| 普通聊天消息 | 现有 APNs（PushService 链路） | 仅推给**不在线**成员（WS 连接表判断）；respect 群免打扰（免打扰 → 只更角标不弹横幅）；同群 60s 内合并（"我们家：3 条新消息"） |
| 高风险播报/求助卡 | V5.1 强提醒（自有通道，已规划） | 无视免打扰；与聊天推送对同一事件**只发一条**（发强提醒则跳过聊天推送） |
| 角标 | APNs badge | = 全部家庭未读之和（服务端算） |

## 5. 媒体消息

| 类型 | 方案 |
|---|---|
| 语音 | AAC(.m4a)，最长 60s；录完先本地 SFSpeechRecognizer 转文字 → 上传 R2（复用现有上传链路）→ 发消息 payload{url, duration, transcript}。**转文字在发送端生成**（免费、隐私不出设备、接收端零等待） |
| 图片 | 压缩至长边 1920 上传 R2，payload 带宽高（气泡按比例占位不跳动）+ 缩略图 |
| 大表情 | 纯 emoji 且 ≤3 个的文本消息，渲染为 64pt 大号（微信同款行为），不引入贴纸资源包（Twemoji 之类后续再议） |

安全与频控：消息 2,000 字上限；发送频率 30 条/分钟/人；语音 5MB / 图片 10MB 上限；所有接口校验"是该群成员"。

## 7. 微信交互对齐清单（验收标准，逐条可查）

**消息列表**
1. 时间胶囊：与上一条间隔 >5 分钟才显示；格式 `HH:mm` / `昨天 HH:mm` / `星期X HH:mm` / `yyyy年M月d日 HH:mm`；
2. 自己的消息右侧绿色气泡（#95EC69），他人左侧白色气泡，头像方圆角 8pt；群聊他人消息显示昵称小字（取 alias > 群昵称 > 用户昵称）；
3. 新消息定位：从后台进入停在"以下是新消息"分割线；在翻历史时来新消息 → 右下角浮"↓ X 条新消息"胶囊，点击回底；
4. 发送状态：转圈（发送中）→ 无标记（已发）→ 红色 ❗ 点击重发（失败）；自己消息下方小字已读状态（"女儿、儿子已读"）；
5. 撤回：长按菜单 2 分钟内可撤，双方显示"你/爸爸 撤回了一条消息"居中灰字；
6. 系统消息（入群/退群/改群名）居中灰色小字："妈妈 加入了家庭"。

**语音**
7. 按住说话：长按变"松开 发送"，全屏遮罩 + 声波，**上滑手指到取消区变红"松开 取消"**（微信同款手势）；
8. 语音气泡宽度随时长变化（1s~60s 线性，min 80pt max 240pt），未播放的语音右上角红点；点击播放，播放中喇叭动画；
9. 语音下方默认展示转文字（比微信更进一步——老人不用长按转，直接看）。

**输入区**
10. 布局（普通模式）：`[🎤/⌨️ 切换] [输入框] [😊] [＋]`，微信同位；长辈模式语音键为主位（见原型 S1）；
11. 文本键盘 return 键 = 发送；输入框随内容长高（最多 4 行）；
12. ＋ 面板：相册 / 拍照（2 项起步，网格布局留扩展位）；😊 面板：系统 emoji 网格；
13. 键盘/面板切换不跳动（高度锁定动画）。

**未读与角标**
14. 家庭 Tab 角标 = 各家庭未读和；切换 sheet 内分家庭显示未读数；
15. 群免打扰时：数字角标变小红点（微信同款语义），强提醒不受限。

**长按菜单**
16. 复制（文本）/ 撤回（自己 2 分钟内）/ 举报 / 查一查是不是骗局（待批）；长辈模式菜单字号放大。

**明确不做**（V5.1 范围外，防止对齐清单膨胀）：引用回复、@提及、转发、消息多选、双击放大、拍一拍、群公告、输入中提示（微信群聊本来也没有）。

## 8. 与既有系统的衔接（相比服务商方案的变化）

| 原方案（腾讯云 Chat） | 自建后 |
|---|---|
| UserSig 签发接口 | ❌ 不需要（JWT 直接鉴权 WS） |
| 群生命周期同步 hook + 对账 cron | ✅ 简化为纯 DB 操作（family_messages 按 groupId 隔离，解散=群禁写+系统消息），**对账 cron 整个砍掉** |
| IM 离线推送挂证书 + 推送去重 | ✅ 只有自己一条推送链路，去重规则简化为"强提醒与聊天推送二选一" |
| 服务商内容安全插件 | 举报 + 拉黑照做（ImModeration 表不变）；敏感词过滤后续可在 send 接口加本地词表 |
| 卡片 = IM 自定义消息 | 卡片 = type=card 的普通消息，编解码自己定义，更简单 |
| 免费 1,000 MAU → 超量计费 | 零外部成本；增量成本 = Railway 常驻 WS 内存（当前规模可忽略） |

**风险变化**：砍掉"服务商故障"风险，新增"自建可靠性"责任 —— 由 §3 的"拉为主"架构兜底（WS 全挂时体验退化为 5s 轮询 + 推送，功能不缺失）。紧急回退开关（familyChatEnabled）保留。
